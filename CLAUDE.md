# KanbanFlow — notes for Claude

This file is project context for future sessions, not user-facing docs (see `README.md` for that). It captures things that aren't obvious from reading the code cold: architectural decisions, data flow, and bugs that were fixed for non-obvious reasons.

## What this is

A real-time multi-user Kanban board. Spanish UI, informal user (typos in prompts are normal, not something to "fix" in their messages). The backend is a small Node server (`server/index.ts`: Express + Socket.io + SQLite) that also serves the built frontend; the browser talks to it only through socket events. There is no session-based authentication: regular users log in by username only and admins with a password (see Auth). Don't add auth infrastructure unless asked — it's an explicit non-goal so far.

## Architecture at a glance

- **Single-component app.** `src/App.tsx` (~2900 lines) holds essentially all state and logic: login, admin dashboard, teams, the kanban board itself, drag-and-drop, presence, the Archivero, the profile/shared/recurring modals. It has not been split into smaller components (small pieces live in `src/ui.tsx`, `src/StatsPage.tsx`, `src/ExportDialog.tsx`). Don't assume a "components/" directory exists — there isn't one.
- **`src/db.ts`** is the client's entire data layer: TypeScript types (`Activity`, `User`, `Team`, `PresenceEntry`, ...), the Socket.io connection, `subscribe*` functions (each wraps a `*:all` event, returns an `Unsubscribe` and replays the cached latest snapshot to late subscribers) and the functions that `emit` writes. All reads are live subscriptions — there is no "refresh" concept; if data appears stale, look for a missing/broken subscription or a missing `broadcast*` on the server, not a missing refetch.
- **`server/index.ts`** owns the SQLite schema (created and migrated at startup with `ALTER TABLE ... try/catch`), every socket handler, and the `broadcast*` helpers that push a whole `*:all` snapshot after any write. The pure rules live in `server/*.ts` modules with `node:test` tests.
- **Routing is hash-based**, not a router library: `#stats`, `#user-<username>`, `#team-<teamId>`, or no hash (own board). Handled by a single `hashchange` listener registered once in `App.tsx` (`useEffect` near the top, ~line 153). It reads from `usersRef`/`teamsRef` (refs mirroring the `users`/`teams` state) rather than the state directly, specifically so the listener doesn't need to be re-registered every time those lists change.

## Data model (SQLite tables, see `initSQLite` in `server/index.ts`)

- `activities` — the tasks. Status is `'todo' | 'doing' | 'done' | 'cancelled'`. `teamId` is set for team tasks, absent/null for personal tasks. `completedAt` is set when status becomes `'done'` and cleared otherwise (see `activity:updateStatus`) — this timestamp, not `createdAt`, drives the 1-day auto-archive. Also `kind`/`sharedId`/`seriesId` (see "Task kinds") and `archived`.
- `users` — `{ username, fullName, role, lastLogin, email, passwordHash, photo, photoUpdatedAt }`. "admin" is a special username (see Auth below), not a role flag; usernames are compared case-insensitively. `passwordHash` and `photo` never go out in `users:all`.
- `teams` — `{ id, name, memberUsernames (JSON array), createdAt }`.
- `presence` — one row per user, `{ username, context, lastSeen }`, written every 8s while the app is open (see the heartbeat `useEffect`). The server only purges rows older than an hour, so a closed tab leaves a stale row behind unless `clearPresence` runs on logout. Readers must always filter by `isPresenceFresh()` (`db.ts`, 20s staleness window) — never trust a presence row's mere existence.
- Also `comments`, `recurrences`, `settings` (see their sections).

**SQLite quirk:** the client sends `undefined` fields as missing keys, so the server normalizes optional values (`assignedBy`, `teamId`, `completedAt`) with `|| null` before writing, and `getActivities` maps null back to `undefined`. If you add a new optional `Activity` column, follow that pattern in `activity:add`/`activity:update` and in `getActivities`.

## Auth

Not session-based auth. Admin accounts (role `admin`, or the built-in `admin`) log in with a password that the server verifies (`auth:login`); regular users log in by username only. **No self-registration:** `user:login` only updates an existing user (`touchLogin` in `server/users.ts`) and replies `unknown_user` otherwise; the login screen shows "Ese usuario no existe". Users are created only through `user:create`, which requires the calling admin's username+password in the payload (`checkAdmin`) — the server never trusts a socket just because it's connected — and never overwrites an existing user (case-insensitive), so it can't be used to change someone's role. `isAdmin` in the client is `user.username.toLowerCase() === 'admin' || user.role === 'admin'`. Still unauthenticated: deleting users/tasks/teams and editing tasks (a known, accepted gap). **Role changes** (`user:setRole`, rules in `server/roles.ts`, tested in `server/roles.test.ts`) are restricted to ONE account, `ROLE_MANAGER = 'inaki'` (case-insensitive): the caller must prove an admin password AND be that user — being an admin isn't enough, and the button only renders for them (`openRoleModal`, `manage_accounts` icon). Promoting needs a password for the new admin (the server gives any admin without one the default `admin` password, so a promotion without a password would leave an open account); demoting clears the password hash; the manager's own role and the built-in `admin` can't be changed. A role change reaches logged-in sessions through an effect that mirrors `users` onto `user.role`.

## Real-time sync

One `useEffect` near the top of `App.tsx` subscribes to `activities`/`users`/`teams`/`presence`/`comments` (each an `*:all` event the server broadcasts on connect and after every mutation). Every write from any tab/device flows back through these listeners automatically. When adding a new piece of server state, prefer this pattern (a `broadcast*` on the server, a cached subscription in `db.ts`, local state in `App`) over one-off request/response reads. Bulk deletes (`activity:clearUser`, `activity:clearTeam`, `user:delete`) run SQL `DELETE`s on the server and then broadcast.

## Views / scoping

`displayedActivities` (computed in the render body, not memoized) is the single source of truth for "which activities does the current view show", and everything else (`historyActivities`, `getCount`, the three kanban columns) filters from it. Its scoping logic:

- Viewing a team (`viewingTeam` set) → all activities with that `teamId`, regardless of who's logged in.
- Otherwise, if admin: either one supervised user's personal activities (`viewingUserAsAdmin` set) or all personal (non-team) activities across everyone.
- Otherwise (regular user, own board): just that user's own non-team activities.

When adding a feature that touches "the board," scope it through `displayedActivities`, not `activities` directly, or it'll leak across users/teams.

**Team-scoped assignment:** the "Asignar A" dropdown in the activity modal restricts options to `viewingTeam.memberUsernames` when on a team board, vs. all non-admin users otherwise (`App.tsx`, ~line 1454). If members get added/removed from a team, existing assigned activities keep their `username` as-is — there's no cascading update.

## The Archivero (archive + 1-day auto-archive)

- The rules live in `src/archive.ts` (tested in `server/archive.test.ts`), shared by the board, the admin dashboard, Productividad and the Archivero modal: `isLive` (an **archived open task** — todo/doing — is shelved and stops counting as open/overdue; archived done/cancelled keep counting as outcomes), `isDoneVisibleOnBoard` (a completed task stays on the board only if `completedAt` is within the last day, or it has no `completedAt` — legacy-data safety net, don't remove), `inArchivero` (anything archived, every cancelled task, and completed tasks older than a day), `matchesTab`/`archiveTabCounts`.
- In `App.tsx`, `scopedActivities` is the context scope (team / supervised user / personal); `displayedActivities = scopedActivities.filter(isLive)` feeds the live views; `archiveActivities` (from `scopedActivities`) feeds the Archivero modal. Any status can be archived (`activity:setArchived` has no status condition); `activity:updateStatus` still resets `archived = 0`.
- Restore in the modal: cancelled → status `todo`; archived → unarchive (keeps its status); aged completed → re-complete onto the board.
- Nothing is deleted automatically; archiving is a display flag plus the `archived` column. If an old task "disappeared", look in the Archivero.

## The drag-and-drop / trash-cancel gesture

This is the most fragile, most-iterated part of the app. Native HTML5 Drag and Drop API (`draggable`, `onDragStart/onDragEnd/onDragOver/onDrop/onDragEnter/onDragLeave`), not a library.

**How it's supposed to work:** holding a drag for 550ms reveals a floating "Suelta aquí para cancelar" button at the bottom of the screen (it does *not* sit on screen permanently — this was a deliberate, explicitly-requested design). Dropping a card there opens a confirm dialog; confirming sets `status: 'cancelled'` and plays a brief "burst" animation on the trash icon.

**Two related bugs were found and fixed here — both are worth understanding before touching this code:**

1. **`dragenter`/`dragleave` flicker on child elements.** The trash zone's icon and label `<span>`s were intercepting `dragenter`/`dragleave` from the parent `.trash-zone` div, causing the hover state (`isTrashHovering`) to flicker on/off as the cursor crossed them — a classic HTML5 DnD quirk (the browser fires enter/leave on whatever element is actually under the cursor, not just the div you attached the listener to). Fixed with `pointer-events: none` on `.trash-zone-icon` and `.trash-zone-label` in `App.css`, so hit-testing always resolves to the parent. **If you add any other child element inside `.trash-zone`, it needs `pointer-events: none` too, or this bug comes back.**

2. **Reveal-timer race condition.** The 550ms reveal timer (`setTimeout(() => setIsTrashZoneVisible(true), 550)`, in `handleDragStart`) could fire *after* a drag had already ended (e.g. the user dropped the card on a normal column in under 550ms), resurrecting the trash button with no further drag events left to hide it again — it would just sit there stuck. Fixed with `isDraggingRef` (a ref, not state — it needs to be readable synchronously inside the timer callback without a stale closure): set `true` in `handleDragStart`, `false` in every drag-ending path (`handleDragEnd`, `handleTrashDrop`, and a window-level `dragend` safety net — see below), and the timer callback checks `isDraggingRef.current` before calling `setIsTrashZoneVisible(true)`. **Any new code path that ends a drag must also set `isDraggingRef.current = false`, or this bug returns for that path specifically.**

There's also a **window-level `dragend` listener** (a plain `useEffect` with `window.addEventListener`, not a React synthetic event) that force-resets all drag/trash state as a safety net. Rationale: `dragend` always fires natively when a drag operation ends, even if the specific card's own React `onDragEnd` handler doesn't run for some reason (e.g. a live update from another user re-renders/unmounts the dragged card mid-drag, detaching it from the tree before React's event delegation can catch the bubbled event). This is real-time collaborative app, so a card genuinely can be removed by someone else's write while you're mid-drag on it.

**Testing note:** the `computer`/browser-automation tool's `left_click_drag` action does **not** trigger native HTML5 DnD events — it only does mousedown/move/up. To test drag-and-drop behavior in a browser, dispatch real `DragEvent` objects via `javascript_tool` instead (`new DragEvent(type, {bubbles:true, cancelable:true, dataTransfer})`), and remember that `setTimeout`/timers can be throttled in background/inactive tabs, so timing-sensitive tests (like the 550ms reveal) need generous waits and should check state after an `await tick(ms)`, not synchronously in the same script tick (React state updates aren't reflected in the DOM until a render commits, which needs an event-loop turn to happen).

## Card compactness (hover-to-expand)

Task cards show only title + dates by default; description and "assigned by" info live inside a `.task-expand` wrapper with `max-height: 0; opacity: 0` that expands on `.task-card:hover`. This is a pure-CSS pattern — no JS state for hover. If a card needs to show its expanded state without hovering (e.g. for a screenshot/test), you can't rely on the `computer` tool's synthetic `hover` action — it does not reliably trigger real CSS `:hover` (confirmed via `element.matches(':hover')` returning `false` after a synthetic hover). Verify visually or via direct DOM/class inspection instead.

## Theming

CSS custom properties (design tokens) drive both themes; dark is default. No hardcoded colors — if you see a raw hex/rgb value being added to `App.css`, that's very likely a bug waiting to happen on theme switch (this happened before: `.task-title { color: #fff }` was invisible on the light theme's white cards, and dark-only `rgba(255,255,255,...)` overlays were used regardless of theme before an `--overlay-rgb` token was introduced to flip per-theme). Light mode is a "soft gray" palette (page `#d6d9de`, cards ~`#e1e4e9`, no white surfaces) chosen to be easy on the eyes — that was an explicit user preference, not a default Vite/React look. Every light text/status color was checked for WCAG AA (>= 4.5:1) against both the page and the card tint; if you change a light token, re-check contrast (the status/danger hues were darkened for this). Productividad (`src/StatsPage.tsx`, charts in `src/StatsCharts.tsx`, count-up hook in `src/useCountUp.ts`, all the math in `src/stats.ts`, tests in `server/stats.test.ts`) keeps red exclusively for overdue; cancelled is gray there. Semantics worth knowing before touching it: the **period** filter never hides open (todo/doing) tasks — done tasks are filtered by `completedAt` (or `createdAt` if missing) and cancelled ones by `createdAt` (there is no cancellation date); the **scope** (personal/teams/all) and period are remembered in localStorage (`statsScope`, `statsPeriod`); "a tiempo" and "cierre medio" only count done tasks that have `completedAt` (legacy ones don't); the weekly trend ignores the period (always the last 8 Monday-start weeks) and omits cancelled tasks. Clicking the donut/KPIs/legend/aging opens an inline task panel (`DrillKey` + `matchesDrill`); Esc closes it. Entrance animations: the page's `ready` flag flips ONE FRAME AFTER the data first arrives (not on mount — the data arrives right after mount, so keying off mount makes the arcs appear already drawn); everything respects `prefers-reduced-motion`.

## Profile (photo, name, username, email)

Clicking your avatar in the header (`openProfileModal`, `isProfileOpen` in `App.tsx`) opens "Mi perfil". The header shows the logged-in person's OWN name and photo/initials for everyone, administrators included (the old generic "AD" icon and "Administrador" title are gone; an admin's subtitle is "Panel de Control General"). On a team board the header shows the team and the avatar isn't a button.

- **Server** (`server/profile.ts`, tests `profile.test.ts`, socket `profile:update` with ack): `updateProfile` validates first (nothing is written on error), then updates `fullName`/`email`/`photo` and, for a new username, `renameUser` carries the rename through `activities.username`/`assignedBy`, `comments`, `recurrences`, `teams.memberUsernames` (JSON) and clears the old `presence` row. A new username must be free (case-insensitive), match `[\p{L}\p{N}._-]{1,32}`, and can't be `admin` or the role manager (`RESERVED_USERNAMES`); those two accounts can't be renamed at all (their rules identify them by username), but can edit name/email/photo. An **administrator account must send its password** (`checkAdmin` + `failAuth` throttle); regular accounts have none (the same known gap as the rest of the app — anyone with a raw socket could edit a regular user's profile).
- **Photo**: resized client-side to a 256 px centre-cropped JPEG (`src/imageUtils.ts`), sent as a data URL and stored in `users.photo` (+ `photoUpdatedAt`). `parsePhoto` only accepts jpeg/png/webp whose bytes really match, <= 400 KB (never SVG). The photo is NOT in the `users:all` broadcast (only `photoUpdatedAt`): it is served by `GET /api/avatar/:username` with `Cache-Control: immutable`, and the client builds `avatarUrl(user)` = `/api/avatar/<name>?v=<photoUpdatedAt>` so a new photo is a new URL. Keep it that way — putting the image in the live users list would bloat every broadcast.
- **Client**: `PhotoProvider` (`ui.tsx`, wrapped around `<App />` in `main.tsx`) subscribes to users and gives every `<Avatar>` a lookup (`src/avatarContext.ts`) by username OR full name, so any Avatar shows the person's photo AND derives its initials from their full name without its call site knowing; initials are the fallback. This matters: screens pass either the username ("Inaki" -> would be "IN") or the full name ("Iñaki Sobera" -> "IS"), and before the lookup resolved the person the same user showed different initials on different screens. After a rename `App` updates `user.username` from the ack so the session continues.

## Email notifications and overdue tasks

- `users.email` is required at the app level (login of a new user, admin "Nuevo Usuario", and a blocking dialog for anyone logged in without one) but nullable in SQLite, because existing rows have none. `user:setEmail` is the only way to change it afterwards; an admin can edit anyone's from the user row.
- Emails go out through the **Gmail API over HTTPS** (`createGmailTransport` in `server/mailer.ts`: refresh token → access token, cached until a minute before expiry → `users/me/messages/send`); there is **no SMTP** any more (nodemailer was removed — the deployment network let HTTPS through but stalled SMTP/STARTTLS). It sends from one Gmail account. Its config is resolved field by field: the `settings` table (`gmail_client_id`, `gmail_client_secret`, `gmail_refresh_token`, `mail_from`, edited from the admin "Correo de avisos" modal) wins over the `GMAIL_CLIENT_ID`/`GMAIL_CLIENT_SECRET`/`GMAIL_REFRESH_TOKEN`/`MAIL_FROM` env vars. The Google OAuth app must be **"In production"**: in "Testing" the refresh token expires after 7 days and mail silently stops (the test button shows `invalid_grant`). `mailer` in `server/index.ts` is a mutable `let`, rebuilt on `settings:saveMail`; always read it at call time (the overdue checker takes `() => mailer`). Without Client ID/Secret/Refresh token, `mailer.enabled` is false and everything is a no-op — never assume mail was sent. Old `smtp_*` rows in `settings` are no longer read (they can be deleted). The email bodies live in `server/emailTemplates.ts` (re-exported from `mailer.ts`): each message is `{subject, text, html}`, sent as multipart/alternative; **everything that comes from user data (titles, descriptions, names) must go through `esc()` before it reaches the HTML**. The greeting uses the recipient's first name, the countdown/lateness needs the caller to pass `today`, and the optional `APP_URL` env var adds an "Abrir KanbanFlow" button (only for http(s) URLs).
- Mail settings sockets: `settings:getMail` (open, returns `hasClientSecret`/`hasRefreshToken` only — **the client secret and refresh token must never be emitted to a client**), `settings:saveMail` and `settings:testMail` (both require an admin's username+password, verified like `auth:changePassword`). The client secret and refresh token sit in plain text in `kanban.db`; `kanban.db` backups are secret too.
- New-task email: `notifyNewTask` in `server/index.ts`, fired from `activity:add` only when the creator (`assignedBy`) is an admin and the assignee is someone else with an email. Fire-and-forget; failures are logged, never block task creation.
- Overdue email: `runOverdueCheck` (`server/overdue.ts`) skips archived tasks and runs at startup, **right after every activity add/update/updateStatus/setArchived** (`void checkOverdue()`), **at local midnight** (`scheduleMidnightCheck`, recomputed with `msUntilNextLocalMidnight` each time) and every 5 min as a safety net; `createOverdueChecker` never overlaps passes — a call during a pass asks for one immediate repeat so nothing waits for the next tick. `activities.overdueNotifiedAt` is stamped only after a successful send, so send failures and users without an email are retried. The stamp is cleared when `endDate` changes or a task leaves done/cancelled (SQL `CASE` in `activity:update` / `activity:updateStatus`).
- Login summary: right after a successful login `showLoginSummary` (`App.tsx`) opens a modal with the user's overdue tasks and the ones assigned to them by someone else since their PREVIOUS login (`buildLoginSummary` in `src/summary.ts`, tests in `server/summary.test.ts`). The previous login is read from the `users` list BEFORE `loginUser` touches `lastLogin` — don't move that read after the login call. With no known previous login nothing is flagged as new; a task that is new AND overdue appears only under overdue; no modal when both lists are empty. Login isn't persisted (a reload asks for the username again), so the summary shows on every login.
- Auto-complete: `autoCompleteAtFull` (`server/autocomplete.ts`), applied in `activity:update`, moves a todo/doing task to done when its progress *changes* to 100 (an already-100% task dragged back to doing doesn't bounce). `updateActivityStatus` (drag) is not affected. A one-time startup sweep (flag `sweep_100_done` in `settings`) moved pre-existing 100% todo/doing tasks to done.
- Team panel vs filters: `src/filters.ts` holds the admin filter as data (`TaskFilter`: statuses any-of, `overdueOnly` AND, users any-of) with `matchesFilter`/`summarizeMatches`/`describeMatches`. The Equipos panel (`teamsExpanded` in `App.tsx`) is MINIMIZED by default (the user asked for that) and the "Todos" button expands it, "Minimizar" collapses it again; a `useEffect` on `filterActive` re-collapses it whenever a filter turns on or off (it also runs on mount, so it must set `false`, not `!filterActive`, or the panel opens on load). Collapsed, it is a strip listing only matching teams under a filter (a team matches when at least one of ITS tasks matches) and all teams otherwise; the "Todos" button expands it again (expanded, it shows every team with matching ones highlighted and the rest dimmed). The stat cards' counts and the per-user map still cover personal (non-team) tasks only. Tests: `server/filters.test.ts`.
- "Overdue" on the client has ONE definition: `src/dates.ts` (`isOverdue`, `daysOverdue`, `overdueLabel`, `countOpenAndOverdue`, `overdueRate`), used by the board, the admin dashboard and `StatsPage`; it is independent of the server's `overdueNotifiedAt` stamp, and `today` is refreshed every minute. Its tests live in `server/dates.test.ts` (src/ is type-checked without Node types, so a `node:test` file can't live there). The server keeps its own copy of the rule in SQL (`server/overdue.ts`) — keep them in sync. Admin dashboard: `overdueOnly` is an extra AND condition next to the OR'ed status filters; the productivity percentage is over OPEN tasks (todo+doing), not all tasks.
- Testing gotcha: a copy of `kanban.db` carries the real Gmail credentials (and overdue stamps), so a test server started on a copy **will send real emails**. Delete the mail rows from the copy (`delete from settings where key like 'gmail_%' or key like 'smtp_%' or key = 'mail_from'`) and start with no `GMAIL_*` env vars before testing.
- Gotcha: `io.on('connection')` registers its socket handlers after awaiting the initial snapshots, so a script client that emits immediately on connect loses the event. Wait ~600 ms first when testing with a raw socket.io client.

## Task kinds: individual, shared, repeating

"Nueva tarea" opens one modal with a **Tipo de tarea** selector (create mode only; `taskType` in `App.tsx`). `activities.kind` is `single` | `shared` | `recurring` (old rows default to `single`); pure helpers and labels live in `src/taskKinds.ts` (tests in `server/taskKinds.test.ts`, which imports from `src/`).

- **Shared** (`server/shared.ts`, tests `shared.test.ts`): ONE activity row per participant, linked by `sharedId`, so it lands on each person's board through the normal `displayedActivities` scoping with its own status/progress. Team progress = average of every copy (`sharedProgress`; cancelled copies don't count, done counts 100), computed on the client from `activities`. Editing title/description/dates/priority reaches every copy (`syncSharedFields`, called from `activity:update`); status/progress stay per person. Deleting a shared task removes only that person's copy. The creator's own copy has no `assignedBy`. Comments live in the `comments` table keyed by `sharedId` (`comment:add`; only someone with a copy, or an admin, can comment); `pruneComments` drops comments whose task no longer exists (called after every delete path via `cleanupAfterDelete`). UI: clicking a shared card opens a comments panel (`commentsForId`, `openCommentsPanel`), while the pencil on the card (a real `IconButton` via `TaskCardBody`'s `onEdit`, with `stopPropagation`) opens the full editor; both render the same `renderSharedPanel` (team progress, per-person progress, thread). Non-shared cards still open the editor on click. Socket: `activity:addShared` (ack). Email: `sharedTaskMessage` to every participant AND every admin, once per address, never the creator (`sharedRecipients`; `notifySharedTask` in `index.ts`).
- **Repeating** (`server/recurrence.ts`, tests `recurrence.test.ts`): has NO start/end dates in the form. The user picks a frequency and the DAY it comes back (a `Rule`: weekday Mon-Fri for weekly/biweekly, day of the month for monthly/quarterly/semiannual, day + month for yearly; `normalizeRule` clamps bad input). The `recurrences` table holds the template + rule (`repeat`, `day`, `month`, `lastDate`, title/description/priority/assignee/team); the first occurrence is created right away (startDate = today, from `activity:add` + `repeat`/`repeatDay`/`repeatMonth`) and every occurrence has `startDate` = the day it was generated and `endDate = ''`, so it never counts as overdue and never triggers the overdue email (the email templates and `TaskDates` cope with a missing end date). `runRecurrences` (startup, local midnight, every 5 min — `checkRecurrences`) creates the occurrence that came due (`nextOccurrence` / `dueOccurrence`; day 31 clamps to the month's last day without drifting; biweekly keeps >= 8 days; monthly uses this month if the day is still ahead, quarterly/semiannual jump 3/6 months; only the latest is created if several were missed). The template is NOT updated when an occurrence is edited. Deleting an occurrence stops the series (`stopSeries`: the template goes away and remaining occurrences become `single`); "Detener repetición" (`series:stop`) does the same without deleting. A series whose user or team is deleted is dropped (`dropSeriesWhere`). `describeRepeat` (`src/taskKinds.ts`) builds the labels ("Cada semana, los lunes").
- Colors: `--color-shared` (violet) and `--color-recurring` (teal) tokens in both themes, contrast-checked (>= 4.5:1). Cards get `kind-shared` / `kind-recurring` (`kindClass`): a top stripe and tint, while the left border keeps showing status; overdue cards keep their red tint.
- `getActivities` LEFT JOINs `recurrences` to expose `repeat`/`repeatDay`/`repeatMonth` on each occurrence. A shared task's card shows the TEAM's progress (the average: badge + violet bar, in every column, `TaskCardBody`'s `teamProgress`) and never one person's own percentage — a person's own progress is only in the comments panel's slider and the editor. It also shows an `AvatarStack` (bottom right) of everyone who has a copy (`SharedStats.members`).

## Shared tasks: new-comment badge and changing participants

- **Unread comments** (`comment_reads` table: `username`, `sharedId`, `lastReadAt`; socket `comments:read`, broadcast `commentReads:all`): a person's unread count is the comments by OTHER people after their last read mark, or after their own copy was created if they never opened it (`countUnread` in `server/shared.ts`, mirrored client-side by `unreadComments` in `src/taskKinds.ts` — keep both in sync). The card shows a filled violet pill (`meta-unread`) only on the logged-in person's OWN copy. Opening the comments panel or the editor of a shared task marks it read (effect on `openSharedId` in `App.tsx`, also for comments arriving while open). **Email**: `notifyComment` → `commentMessage` goes only to the other participants with an email for whom the comment is their FIRST unread one (`commentRecipients`), so a busy thread never floods inboxes; admins who aren't participants are not emailed.
- **Changing participants** (`setParticipants` in `server/shared.ts`, socket `shared:setParticipants` with ack): the editor of a shared task (pencil) shows the same checkbox picker as creation; saving diffs it against the current copies. New people get a copy at todo/0% and the same "shared task" email; removed people lose their copy and progress (the client asks for confirmation first; comments stay). At least one person must remain, only a participant or an admin may change it, and on a team task only team members can be added.

## Excel export

- `src/export.ts` (`buildExportData`, `safeSheetName`; tested in `server/export.test.ts`) decides what is exported: every user's tasks that are **not archived** (any status — done and cancelled included), grouped per person, Spanish labels, overdue flag/days; one sheet per person that has tasks (names sanitized to Excel's rules: <= 31 chars, no `\ / ? * [ ] :`, unique) plus "Resumen" (all users, even with 0 tasks) and "Todas".
- `src/exportExcel.ts` writes the workbook with **exceljs**, imported dynamically so its ~930 KB chunk only loads when someone exports (the main bundle stays small). Calendar days are written as UTC midnight and timestamps as local wall-clock time so Excel shows what the app showed. `exportAllTasks` is the single entry point used by both the admin header button and the Productividad page; feedback goes through `useToast`/`Toast`.
- The Excel export ignores the Productividad period/scope filters on purpose (it is a full dump of live work, not a report of the current view). Only admins see the button.
- Both export buttons (admin header and Productividad) open `ExportDialog` (`src/ExportDialog.tsx`), which ASKS every time: only the current tasks, or the current ones plus the archived ones (`buildExportData`'s `includeArchived`; the dialog shows both counts and disables the second option when nothing is archived). With archived included the sheets get an "Archivada" (Sí/No) column, the Resumen an "Archivadas" count, archived rows go after each person's current ones, and the file is named `KanbanFlow_tareas_con_archivadas_<date>.xlsx`; the default export is unchanged. An archived open task is never flagged overdue (`isOverdue`).

## Google Calendar sync

`syncWithGoogleCalendar` (~line 259) is optional and self-contained: if no `googleClientId` is set (stored in `localStorage`, entered via the sync modal), it runs a **simulated** sync (just a timeout + success message) — no real network calls. If a Client ID is provided, it uses Google Identity Services (`window.google.accounts.oauth2`, loaded via a `<script>` tag in `index.html`) to get an OAuth token, then POSTs each of the current view's `displayedActivities` to the Google Calendar API as events. This is entirely client-side; there's no server component and no token storage beyond the browser session.

## Docker / deployment

`Dockerfile` is a two-stage build (`node:22-alpine` build → `node:22-alpine` runtime — no nginx). The runtime stage runs `npm run server` (`tsx server/index.ts`), and that same Express process serves the built frontend (`dist/`, copied from the build stage) via `express.static` plus a catch-all `sendFile(index.html)` fallback — see the `distPath`/`existsSync` block near the bottom of `server/index.ts`. One container, one port (`PORT`, default 3001). `kanban.db` is written to `DB_PATH` (default `/app/data/kanban.db` in the image, overridden in dev via env var to the old `../kanban.db` default), which is declared as a `VOLUME` so it survives rebuilds — mount it, or the database resets on every redeploy.

`sqlite3`'s native addon needs a C/C++ toolchain to compile, so both Dockerfile stages `apk add python3 make g++` before `npm ci`; the runtime stage `apk del`s them again afterward to keep the final image slim (the compiled `.node` binary doesn't need the toolchain present at runtime, only during install). `tsx` lives in `dependencies`, not `devDependencies` — the runtime stage installs with `--omit=dev` and still needs it to run the server.

`VITE_BACKEND_URL` is optional at build time. `src/db.ts` defaults to `window.location.origin` in a production build (correct for this single-container setup, where the API and frontend share a port) and to `http://localhost:3001` in dev (`import.meta.env.DEV`, since Vite's dev server and the API run on different ports locally). Pass `--build-arg VITE_BACKEND_URL=...` only for a split deployment where the frontend and API are on different hosts.

The Firebase code and its `VITE_FIREBASE_*` variables were removed (nothing used them since the move to the Express/SQLite server); the only build-time variable left is the optional `VITE_BACKEND_URL`.

## UI primitives

`src/ui.tsx` holds the presentational primitives (`Icon`, `IconButton`, `Avatar`, `Meta`, `TaskDates`, `FieldLabel`, `Segmented`, `TaskCardBody`, `MiniTaskCard`...). The UI is icon-first: tooltips use `data-tip`, not `title`, for migrated icons (the board cards' title tooltip included). They are drawn by ONE `<TooltipLayer />` (`src/ui.tsx`, rendered in `main.tsx`), not by a CSS `::after`: it follows the INNERMOST hovered `[data-tip]` (a parent's tip never shows under a child's, e.g. the online-users pill vs its avatars), is `position: fixed` (a modal's `overflow` can't clip it), flips below when there's no room above and is clamped to the window. Don't reintroduce a `[data-tip]::after`. It appears with a short, minimal fade/slide (`tipIn`, 160 ms, no overshoot — the user rejected a bouncier version) that uses the separate `scale`/`translate` properties because `transform` is taken by the positioning; `data-side` (above/below) sets its origin; disabled under `prefers-reduced-motion`. Pointer hover only; keyboard `:focus-visible` shows it too; hidden on touch (`hover: none`). When testing with Playwright, `hover`, wait ~0.5 s (350 ms delay) and screenshot in separate steps — parallel calls race. Board cards keep their `<div draggable>` wrapper in `App.tsx` (the drag handlers live there; `TaskCardBody` only renders the inside). The short date format lives in `src/dates.ts`.
